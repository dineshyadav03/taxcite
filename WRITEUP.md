# Portfolio writeup

## Short version (LinkedIn post)

I built a RAG system over Indian income tax law — because a specific, checkable failure of large language models made the case for it better than a general pitch would.

**The gap:** India's Income-tax Act, 2025 came into force on 1 April 2026, completely renumbering the tax code it replaced. Section 139 of the old Act governs who has to file a return. Section 139 of the new Act is an unrelated provision about Special Economic Zone developer income. The new Act's effective date falls after most current language models' training cutoffs — including the model I built this with. I checked, directly, before building anything: does the assistant confuse the two Acts' section numbering when asked. It does. That's not a hypothetical RAG pitch, it's a reproduced failure.

**What I built:** a citation-grounded system over both Acts (536 sections of the 2025 Act, 707 of the 1961 Act), then — after being asked directly which of the ten commonly-cited RAG patterns the system actually used — all ten of them, as independently selectable, independently verified pipelines over the same corpus: Simple, Memory, Branched, HyDE, Adaptive, Corrective, Self-RAG, Agentic, Multi-modal (prose plus a separately-extracted table index, since rate schedules extract as garbage prose otherwise), and Graph (a 3,683-edge cross-reference graph built from the statute's own internal citations). Every pattern returns a trace of what it actually did, not just an answer — sub-questions asked, chunks graded and why, tool calls made, references followed.

**Why it's not just a chatbot wrapper:** the extraction problem alone required rejecting the obvious approach. A naive regex for "section boundaries" on the raw PDF text produced 5,471 false positives on one Act — the actual signal was typographic, not textual: real section numbers are set in bold in the source PDF, table row numbers aren't. Getting from that discovery to 100% section coverage on the 2025 Act took three more rounds of finding and fixing silent data loss, the last of which was a length-ceiling heuristic quietly discarding a 43,850-character section that had absorbed sixty years of amendments.

**Verification found real bugs, not just confirmed the design.** Exercising all ten patterns with queries chosen to trigger each one's specific mechanism surfaced two defects: a section-lookup function that could silently starve one Act's content when the same section number existed in both, and a Groq API failure mode that crashed the self-critique pattern outright instead of degrading. Both were found, fixed, and individually re-verified — not assumed fixed because the code changed.

Runs entirely on free infrastructure: Voyage AI's hosted embedding API and Groq's hosted generation API, both free-tier, no payment method entered anywhere in the stack even where one would have unlocked faster rate limits at no financial cost.

Repo: [github.com/dineshyadav03/taxcite](https://github.com/dineshyadav03/taxcite)

## Longer version (for a README/portfolio page or interview talking points)

**The problem, stated precisely enough to be checkable.** Most RAG pitches assert that a base LLM "doesn't know" niche or recent information. That's true but underspecified — it doesn't tell you whether the model fails by refusing, by hedging, or by confidently answering wrong. For a legal or tax RAG system specifically, the failure mode that matters is the third one, because it's the one a reader can't detect locally: a fluent, well-formatted answer citing a real-sounding section number, with nothing about its surface form signaling that the number is wrong. I checked, before scoping this project, whether that specific failure actually occurs with the new Income-tax Act — asking about a section by number and getting an answer that silently drew from the old Act's numbering instead. It did. That result is what the project is actually built to fix, not a case built backward to justify a RAG demo.

**Getting the corpus right took more engineering than the retrieval layer did.** The source PDFs are Gazette-of-India typeset documents: two-column layout with a marginal-caption column whose side alternates by page, Schedule tables that read as noise when flattened to prose, and section numbering that isn't reliably distinguishable from surrounding text by pattern alone. A first attempt at boundary detection — regex over flattened text — produced 5,471 candidate section boundaries against a true count of 707. The actual discriminating signal turned out to be typographic: real section numbers render in a bold font variant; table and Schedule row numbers render in the regular weight of the same font. That's not a fact I assumed — I confirmed it by inspecting the PDF's character-level font metadata directly before building extraction logic around it.

**Reaching 100% section coverage exposed three separate silent-data-loss bugs, each caught by tracing one specific missing section back to source rather than trusting an aggregate count.** Two were fixed max-length ceilings meant to catch runaway extraction — 8,000 characters, then 40,000 — that instead discarded real, heavily-amended sections. The 1961 Act's Section 139 ("Return of income") runs 43,850 characters after sixty years of Finance Act amendments layered onto one provision; no fixed ceiling is a sound heuristic for how long real statutory text can legitimately run. The fix was removing the ceiling entirely, not raising it again.

**The embedding infrastructure fought back twice before working, and both fights were instructive.** I was asked explicitly to move all compute off the local machine onto free hosted APIs. Google's Gemini Embedding API looked generous on general documentation, but its embedding endpoint specifically enforces an undocumented 1,000-request daily cap, visible only in the full structured error body — not in any rate-limit page I found by searching first. Voyage AI's genuinely free tier (no payment method on file) throttles to 3 requests per minute; a card would lift that while usage itself stayed free, and I chose not to ask for one, because the project's zero-budget premise is about avoiding financial exposure entirely, not about minimizing a bill that would in this case have been zero either way. The actual fix was building the index build to be resumable and to persist incrementally per batch — a multi-hour run against a hard 3-requests-per-minute ceiling has to survive being interrupted, and it was, more than once, including once by my own mistaken diagnosis that a slow-but-working process had hung when it hadn't.

**The scope grew because I was asked a direct comparison question and answered it honestly.** Partway through, I was asked which of the ten commonly-cited RAG patterns the system actually implemented. The honest answer was one — Simple RAG, plus a single hand-built hybrid-retrieval trick for exact section-number queries. I said so plainly rather than describing the one pattern in language that made it sound like more. The response was a direct instruction to build all ten, properly, as independently verifiable pipelines rather than a checklist of half-implementations. I built a shared retrieval substrate — exact-match lookup, vector search, table search, graph traversal, all in `retrieve.py` and `graph.py` — specifically so the ten patterns differ only in how they call into shared, single-source-of-truth code, not in ten separately-maintained retrieval implementations that could drift out of sync with each other.

**Verification was designed to catch each pattern doing the wrong thing while still looking fine, not to confirm each pattern ran without an exception.** For each of the ten patterns I chose a query designed to specifically exercise its mechanism — a follow-up question with no antecedent for Memory, a genuinely colloquial phrasing for HyDE, a question naming a section that exists differently in both Acts for the exact-lookup path, a section with real graph edges for the Graph pattern (an earlier test on a section with zero outgoing references would have looked like a bug and wasn't one — I checked the graph data directly before concluding that). This surfaced two real defects:

- **Silent Act-starvation in the exact-section lookup.** When a section number exists in both Acts, the original code sorted every matching chunk by `(act_id, chunk_index)` before truncating to the result limit. Because one Act's identifier sorts alphabetically before the other's, and because the same section number can hold vastly more content in one Act than the other, the alphabetically-first Act could consume the entire result before the second Act's version of the same section was ever considered. I caught this because the failing case didn't produce an error — it produced a plausible-sounding, wrong answer: the system reported that Section 139 didn't exist in the 2025 Act, because the 2025 Act's real content for that section had been silently excluded from what it ever saw. The fix interleaves results across Acts instead of sorting flat; because the buggy function was shared infrastructure, the fix improved the original Simple RAG pipeline too, not only the newly-added patterns.
- **An unhandled hard-failure mode in Groq's structured-output API.** Groq's JSON mode can return a hard `400` error on a truncated generation rather than returning the truncated text for a caller to salvage — a different failure class from malformed-but-present JSON, which the system already handled by regex-salvaging the largest parseable object from a response. This crashed the Self-RAG pattern's self-critique step outright. I fixed it once, at the single shared LLM-calling function every pattern uses, converting the hard API exception into the same error type every JSON-mode caller already knew how to catch — rather than patching each of the several call sites that could have hit the same failure independently.

**The evaluation methodology was chosen to measure the actual claim, not a proxy for it.** Twenty hand-written questions, each with ground truth built by reading real, already-extracted section content — not assumed from general tax-law familiarity, and not trivially available for the 2025 Act specifically, whose section titles live in a PDF caption column the extraction pipeline deliberately excludes. I measured retrieval hit rate, refusal accuracy, and citation accuracy rather than a RAGAS-style faithfulness score, because this project's actual claim is "cites the right Act and section," and a general prose-faithfulness metric measures something adjacent to that, not that. The first full run scored 100% retrieval hit rate and 100% refusal accuracy, but only 90% citation accuracy — and all three failing cases shared the same root cause: retrieval had already found the correct section every time, but a confidence-refusal threshold left over from an earlier, different embedding model was rejecting the match anyway. I measured the actual distance distribution of genuinely relevant matches versus verified off-corpus queries under the new embedding model, recalibrated the threshold against real numbers instead of a guess, and individually re-verified the three previously-failing questions before reporting the fix as done.

**What I'd tell an interviewer about the parts that didn't go smoothly.** A mid-session pivot moved this project from an entirely different scope — a code-search RAG over FastAPI's own source, abandoned before any pipeline code existed — through several narrower ideas before landing on Indian income tax law specifically, and the repo and local folder both still carry the scar of that history in early commit messages even after being renamed to match the final project. Renaming the local folder mid-session hit a Windows file lock that a standard shell rename command couldn't clear even after killing every process I could find referencing the path; a different tool (PowerShell's `Move-Item`) succeeded immediately on the identical path, which was a useful reminder that a tool-specific failure isn't always evidence the operation itself is blocked. And more than once during the long embedding-index build, I misjudged a slow-but-healthy background process as stuck and killed it prematurely — the fix wasn't a smarter timeout, it was making the build resumable and incrementally-persisted in the first place, so a wrong call cost minutes of re-verification rather than hours of lost work.

**What's next.** Hybrid BM25-plus-vector retrieval to close the one retrieval gap that's real and currently unfixed — a topical query that never names a section number still relies on pure similarity search, which can miss the best match the same way any similarity search can. Table-aware extraction inside the main prose pipeline, not only in the separate multi-modal index, so a prose-only pattern retrieving a table-heavy section doesn't still get the garbled version. And public deployment, which is scoped and ready but needs a hosting sign-in this assistant can't complete on the user's behalf.
